# Exercise 5 evidence: investigating a DNS and TLS failure

This investigation uses the **simulation supplied with the exercise**. The
hostnames, IP addresses, commands, and outputs below are invented for the lab.
I did not run them, and they are not results from `caelonk.me`.

## 1. Setting and prediction

**Setting:** the supplied simulation. `site.lab.example` should reach a new
Railway deployment. The Railway-provided URL already returns the current page
and database content, Cloudflare is authoritative for `lab.example`, the site's
record is DNS only, and the ownership TXT record has already verified.

**Failed check:** `dig site.lab.example A +noall +answer`, then
`curl -Iv https://site.lab.example/`.

**Prediction:** `dig` returns a CNAME to the Railway target. `curl` connects to a
Railway address, gets a certificate for `site.lab.example` that verifies, and
receives an HTTP 200.

## 2. Failed check and evidence

Simulated output supplied with the exercise, read on 2026-10-12:

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

**Actual result:** DNS still returned the old Azure address, curl connected
there, the server presented a certificate for a different name, and curl
stopped with error 60 before any HTTP response.

## 3. Diagnosis

Written before opening the simulated follow-up.

The connected address matches the stale A record, and the certificate belongs
to the old VM. That means TLS failed because the client reached the wrong
server, not because of a certificate problem on Railway.

What remains uncertain: one resolver's answer doesn't show what other resolvers
have cached. From what I can tell, I can't yet confirm Railway will serve a
valid certificate for the name until traffic actually reaches it.

## 4. Repair and repeated check

**Proposed change (before the follow-up):** The problem record is the A record
for `site.lab.example`, which still points to the old Azure server at
`198.51.100.24`. This record is the only thing sending traffic to the wrong
place, since the Railway deployment already works at its own URL.

I would delete that A record and create a CNAME from `site.lab.example` to
`current-app.up.railway.app`, left as DNS only. The old record has to be
removed rather than kept alongside the new one, because a CNAME can't share a
name with other records.

The supporting evidence is that `dig` returned `198.51.100.24` and curl
connected to that same address. Because the client reached exactly the address
DNS gave it, the wrong certificate came from following a stale record, not from
a certificate problem on Railway.

Simulated follow-up supplied with the exercise. A lab operator made one record
change. I interpreted this output; I did not run it:

```text
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

| | Before | After |
|---|---|---|
| DNS answer | `A 198.51.100.24` | `CNAME current-app.up.railway.app.`, then `A 203.0.113.44` |
| Connected address | `198.51.100.24` | `203.0.113.44` |
| Certificate name | `CN=old-vm.lab.example` | `CN=site.lab.example` |
| HTTP result | none, curl error 60 | `HTTP/2 200` |

**Record change and comparison with my proposal:** The A record was replaced by
the CNAME. The DNS fault came first; the TLS error was downstream of it. Every
row of the table moved the way my DNS diagnosis predicted. One uncertainty is
left: `curl -I` only fetches headers, so a 200 doesn't prove the page shows
current database content.

## 5. What you learned

The error I see isn't always where the problem is. Curl reported a certificate
error, so it looked like a TLS problem. The real fault was one layer earlier:
DNS sent me to the wrong server, and that server correctly presented its own
certificate for a different name. The TLS failure was a symptom.

Another check is `curl --resolve site.lab.example:443:<ip> https://site.lab.example/`.
`curl --resolve` makes curl skip DNS and connect to an address I choose, while
still requesting `site.lab.example` and checking the certificate for that name.
This lets me test the server directly without waiting for DNS to change.

I would use the Railway deployment's address, since that is the server the site
should reach. I would get it with `dig current-app.up.railway.app A +short`,
which works even while `site.lab.example` still points to the old server.

If `--resolve` succeeds with a valid certificate and an HTTP 200 while the
normal check fails, the Railway side is working and the problem is DNS. If
`--resolve` also fails, the problem is in TLS or the application, and changing
DNS alone would not fix it.
